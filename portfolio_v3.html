That's still how I learn, most days, usually starting with "what happens if I just try this."

FLAGSHIP PROJECT

LLM Security Audit Framework

A security assessment framework for LLM-integrated applications — maps the architecture first, then applies only the checks that actually matter.

Most security tooling assumes instructions and data live in different places. LLM applications don't work that way — a system prompt and a user's message end up in the same context window, and that one fact breaks a lot of assumptions older scanners rely on.

This framework starts by mapping an application's architecture — its system prompt design, input pipeline, output pipeline, connected tools, and whatever security layers already exist — and only then runs the checks that are relevant to what it finds. An app with no tool-calling skips tool schema validation entirely. An app with a static system prompt skips the checks built for dynamic injection. That mapping step is what keeps an audit fast instead of exhaustive by default.

From there it works through five domains — system prompt hardening, input validation, output validation, tool & function security, and threat tracking & alerting — each producing concrete, code-level findings rather than vague advisory language. Recommendations also adapt to where the application actually runs, from a single local script to a distributed, load-balanced service.

Under the hood it's a multi-agent workflow — separate agents handle threat analysis, security validation, evidence collection, and report generation, with confidence-based routing deciding when a finding needs deeper scrutiny. The backend runs on FastAPI, orchestrating local/open-source models through Ollama and GPT-OSS, with audit findings persisted through SQLAlchemy into MySQL.
